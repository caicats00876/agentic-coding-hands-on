# vibe-order MVP 設計（アーキテクチャ / データ構造 / API / タスク分割）

## Context

`vibe-order/docs/requirements.md` の要求仕様をもとに、Day3 で作ったモノレポ雛形（shared / backend / frontend、`GET /health` のみ）の上に、リアルタイム オーダー管理システムの MVP を作る。
この設計の目的は、`packages/shared` で契約（Zod スキーマと純粋関数）を先に固め、そのあと `packages/backend` と `packages/frontend` を**別々に並行して実装できる**ようにすることである。
そのために、機能ごとに 30 分以内のタスクに分け、それぞれにテストで確かめられる受け入れ条件を付ける。

### 合意済みの決定事項（2026-10-23）

| 論点 | 決定 |
|---|---|
| 注文の単位 | 1 注文 = 複数の品目（orders + order_items）。状態とキャンセルは注文ごとに扱う |
| キッチン画面 | 1 画面で 受付 → 調理中 → 提供済 のすべてを操作する。状態は要求仕様どおり 3 つ（＋キャンセル済） |
| 席の識別 | 客がケータイで QR を読む。QR の URL には推測できない**席トークン**を入れる |
| 来店の区切り | 席ごとの**来店セッション**。QR を読んだとき、その席に有効なセッションが無ければ作る。同じ席の複数のケータイは同じセッションを共有する。キッチン画面の「会計済（退席）」でセッションを終える。終わったセッションでは注文できない |
| 画面の保護 | 客は席トークン → セッショントークンで操作する。スタッフ用の API と WS には環境変数 `STAFF_KEY` が必要 |
| 注文ガチャ | **MVP に入れる**。「提供済」にするときにサーバーが抽選し、当たれば利用中の別の席に届ける。注文した客の進捗画面の最後に「お待たせしました」か「残念…」を表示し、届いた席には「おすそ分けが届きました」を表示する。代金は注文した席の会計に残す |
| 即時 | リロードしなくても画面が更新されること |
| 席の数 | `SEAT_COUNT`（環境変数、既定 20）で変えられる。非機能要件（20 席の同時接続）は 20 で検証する |
| 研修での確認 | 客の画面も PC のブラウザで動けば十分とする。QR の URL をブラウザで直接開いて確かめる。Codespaces のポートは Private なので、ケータイからの接続は確かめない。E2E も PC の Chromium だけで行う |

### 技術選定（新しい依存は `ws` と `@types/ws` だけ）

| 用途 | 採用 | 理由 |
|---|---|---|
| SQLite | **Node 24 標準の `node:sqlite`（`DatabaseSync`）** | 標準機能で足りる（依存を増やさない）。`node -e "require('node:sqlite')"` で警告なしに読み込めることを確認済み。使い方は Node 公式ドキュメントで確かめてから書く |
| WebSocket（サーバー） | `@hono/node-server` 2.1.5 の `upgradeWebSocket` ＋ **`ws`（MIT）と `@types/ws`** | `node_modules/@hono/node-server/README.md` の「WebSocket」節に「install `ws` (and `@types/ws`) ... provide a `WebSocketServer`」とある。追加するのはこの 2 つだけ。版は 7 日ルールで決め、memo.md に記録する |
| WebSocket（クライアント、テスト） | ブラウザと Node 24 標準の `WebSocket` | 依存を増やさない |
| 画面の切り替え | `location.pathname` で分ける（ルーターのライブラリは入れない） | 画面は 2 つだけなので KISS |
| QR 画像 | MVP では作らない。スタッフ画面に席ごとの URL を表示し、QR は外部のツールで作る | QR の生成には依存が必要になるため。画面での生成は将来の拡張 |

## 1. 全体アーキテクチャ

```
 客のケータイ (/s/:seatToken)          キッチン画面 (/kitchen)
        │  REST + WS                          │  REST + WS (X-Staff-Key)
        ▼                                     ▼
 ┌──────────────── Vite dev / preview（:5173）──────────────────┐
 │  React SPA     proxy: /api → :3000、/ws → :3000（ws: true）     │
 └───────────────────────────────┬──────────────────────────────┘
                                 ▼
 ┌──────────────── backend（Hono + @hono/node-server, :3000）────┐
 │ routes/customer.ts  routes/staff.ts  ws/handler.ts             │
 │        │                  │               ▲                    │
 │        ▼                  ▼               │ publish            │
 │   services/（注文・セッション・ガチャ）──▶ ws/hub.ts（購読管理）    │
 │        │                                                       │
 │        ▼                                                       │
 │   db/（node:sqlite、schema.sql、seed）→ DB_PATH（既定 data/vibe-order.db）│
 └────────────────────────────────────────────────────────────────┘
 shared: Zod スキーマ、型、純粋関数（状態遷移、合計金額、WS メッセージ）
```

- 同じオリジンで配信する（Vite の proxy）。そのため CORS の設定は要らない。Codespaces で転送するポートは 5173 だけにし、公開範囲は Private か Organization とする
- backend は `createApp({ db, hub, config, random, now })` のように依存を引数で受け取る。テストでは `:memory:` の DB、偽の乱数、固定した時刻を渡す。`index.ts` は起動処理だけにする（カバレッジの対象外のまま）
- 書き込みはすべて services を通す。services は DB を更新したあと Hub にイベントを publish する。routes は検証と HTTP への変換だけを行う
- 即時反映: 変更は WS で配信し、クライアントは受け取った注文 DTO で状態を置き換える。WS が再接続したら REST で一覧を取り直し、切断中に取りこぼしたイベントを補う

## 2. データ構造（SQLite のテーブル定義）

- すべて `STRICT` のテーブルにし、起動時に `PRAGMA foreign_keys = ON` と `PRAGMA journal_mode = WAL` を実行する
- 金額は円の整数。時刻は ISO 8601 の UTC 文字列
- 状態の値（DB と API で共通）: `received`（受付）、`cooking`（調理中）、`served`（提供済）、`cancelled`（キャンセル済）

```sql
CREATE TABLE IF NOT EXISTS menu (
  id          INTEGER PRIMARY KEY,
  name        TEXT    NOT NULL,
  price       INTEGER NOT NULL CHECK (price >= 0),
  description TEXT    NOT NULL DEFAULT '',
  category    TEXT    NOT NULL,              -- 例: main / side / drink / dessert
  sold_out    INTEGER NOT NULL DEFAULT 0 CHECK (sold_out IN (0, 1)),
  sort_order  INTEGER NOT NULL DEFAULT 0
) STRICT;

CREATE TABLE IF NOT EXISTS seats (
  id     INTEGER PRIMARY KEY,
  label  TEXT NOT NULL UNIQUE,               -- 例: "1" 〜 "20"
  token  TEXT NOT NULL UNIQUE                -- QR の URL に入れる。crypto.randomBytes(16) を base64url にしたもの
) STRICT;

CREATE TABLE IF NOT EXISTS sessions (        -- 来店単位
  id          INTEGER PRIMARY KEY,
  seat_id     INTEGER NOT NULL REFERENCES seats(id),
  token       TEXT    NOT NULL UNIQUE,       -- 同じ席のケータイで共有する。randomBytes(16) の base64url
  started_at  TEXT    NOT NULL,
  ended_at    TEXT                           -- NULL なら利用中
) STRICT;
-- 1 つの席で利用中のセッションは 1 つだけ
CREATE UNIQUE INDEX IF NOT EXISTS sessions_one_active_per_seat
  ON sessions(seat_id) WHERE ended_at IS NULL;

CREATE TABLE IF NOT EXISTS orders (
  id                    INTEGER PRIMARY KEY,
  session_id            INTEGER NOT NULL REFERENCES sessions(id),  -- 注文した来店（会計先）
  status                TEXT    NOT NULL DEFAULT 'received'
                        CHECK (status IN ('received','cooking','served','cancelled')),
  delivered_session_id  INTEGER REFERENCES sessions(id),           -- 提供済にしたとき決まる。ガチャが当たれば別の来店
  created_at            TEXT    NOT NULL,
  updated_at            TEXT    NOT NULL
) STRICT;
CREATE INDEX IF NOT EXISTS orders_session ON orders(session_id);
CREATE INDEX IF NOT EXISTS orders_status  ON orders(status);

CREATE TABLE IF NOT EXISTS order_items (
  id          INTEGER PRIMARY KEY,
  order_id    INTEGER NOT NULL REFERENCES orders(id),
  menu_id     INTEGER NOT NULL REFERENCES menu(id),
  name        TEXT    NOT NULL,              -- 注文した時点の名前と価格を残す（会計がぶれないように）
  unit_price  INTEGER NOT NULL CHECK (unit_price >= 0),
  quantity    INTEGER NOT NULL CHECK (quantity BETWEEN 1 AND 10)
) STRICT;
```

- 初期データ: `migrate()` のあとに、`menu` が空なら 10 品を入れる（うち 1 品は `sold_out = 1`）。`seats` の数が `SEAT_COUNT` より少なければ足りない分を作る。何度実行しても結果が変わらない
- テストデータのリセット: ユニットと結合テストは毎回 `:memory:`。E2E は起動前に `DB_PATH` の一時ファイルを消す
- `data/` は `.gitignore` に追加する
- 会計（セッションの合計）= そのセッションの注文のうち `cancelled` 以外の `Σ unit_price × quantity`。ガチャで他の席に届いた注文も含める

## 3. 共有スキーマ（packages/shared）

| ファイル | 中身 |
|---|---|
| `errors.ts` | `ErrorResponseSchema = { error: { code, message } }`。`code` は `VALIDATION_ERROR` / `UNAUTHORIZED` / `NOT_FOUND` / `SESSION_ENDED` / `MENU_SOLD_OUT` / `INVALID_TRANSITION` / `UNFINISHED_ORDERS` |
| `menu.ts` | `MenuItemSchema { id, name, price, description, category, soldOut }` |
| `order.ts` | `OrderStatusSchema`、`OrderItemInputSchema { menuId: int>0, quantity: int 1..10 }`、`CreateOrderRequestSchema { items: 1..20 件、menuId の重複なし }`、`OrderItemSchema { menuId, name, unitPrice, quantity }`、`OrderSchema { id, sessionId, seatLabel, status, items, total, delivery: null \| { seatLabel, isGacha }, createdAt, updatedAt }`、`UpdateOrderStatusRequestSchema { status: 'cooking' \| 'served' }` |
| `orderRules.ts` | `canTransition(from, to)`、`nextStatus(status)`、`canCancel(status)`、`orderTotal(items)`、`sessionTotal(orders)` |
| `session.ts` | `JoinSessionResponseSchema { sessionToken, seatLabel }`、`CustomerSessionSchema { seatLabel, startedAt, total, orders: Order[], gifts: Order[] }`、`StaffSessionSchema { id, seatLabel, startedAt, total, unfinishedCount }`、`SeatSchema { label, token }` |
| `ws.ts` | `ClientMessageSchema`、`ServerMessageSchema`（`type` で判別する discriminatedUnion。4 章を参照） |

- 客向けの `Order.delivery` は、注文した客には `{ seatLabel, isGacha }` を返す。届いた席が自分の席かどうかは `isGacha` で判断する（自分の席なら false）。届いた側の `gifts` では、注文した席の番号を出さない（`seatLabel` は空にする）
- `index.ts` からすべて export する

## 4. REST API と WebSocket メッセージ

### 共通

- 入力（path、query、body）はすべて shared の Zod スキーマで検証する。失敗したら `400 VALIDATION_ERROR`
- エラーの本文は `ErrorResponseSchema` の形にする
- 客の認証: ヘッダー `X-Session-Token`。知らないトークンなら `401 UNAUTHORIZED`、終わったセッションなら `410 SESSION_ENDED`
- スタッフの認証: ヘッダー `X-Staff-Key` を `STAFF_KEY` と `crypto.timingSafeEqual` で比べる。違えば `401`
- 他のセッションの注文は「存在しない」として `404` を返す（存在するかどうかを漏らさない）

### 客向け

| メソッド / パス | 認証 | 入力 | 成功 | 主なエラー |
|---|---|---|---|---|
| `GET /api/menu` | なし | - | 200 `MenuItem[]`（sort_order 順） | - |
| `POST /api/seats/:seatToken/session` | 席トークン | - | 200 `JoinSessionResponse`（利用中のセッションに入る。無ければ作って 201） | 404 席が無い |
| `GET /api/session` | Session | - | 200 `CustomerSession` | 401 / 410 |
| `POST /api/session/orders` | Session | `CreateOrderRequest` | 201 `Order`（status = received） | 400、404 メニューが無い、409 `MENU_SOLD_OUT`、410 |
| `POST /api/session/orders/:orderId/cancel` | Session | - | 200 `Order`（cancelled） | 404、409 `INVALID_TRANSITION`（received 以外）、410 |

### スタッフ向け（すべて `X-Staff-Key` が必要）

| メソッド / パス | 入力 | 成功 | 主なエラー |
|---|---|---|---|
| `GET /api/staff/orders` | query `status`（カンマ区切り、既定 `received,cooking`） | 200 `Order[]`（古い順） | 400 |
| `PATCH /api/staff/orders/:orderId/status` | `UpdateOrderStatusRequest` | 200 `Order`。`served` のときガチャを抽選し `delivery` を決める | 404、409 `INVALID_TRANSITION`（received→cooking、cooking→served 以外） |
| `GET /api/staff/sessions` | - | 200 `StaffSession[]`（利用中のみ、席の番号順） | - |
| `POST /api/staff/sessions/:sessionId/close` | - | 200 `StaffSession`（ended） | 404、409 `UNFINISHED_ORDERS`（received / cooking が残っている） |
| `GET /api/staff/seats` | - | 200 `Seat[]`（画面で `location.origin + /s/ + token` を作り、QR 用に表示する） | - |

### 注文ガチャ（`services/gacha.ts`）

- `cooking → served` のとき、`random() < GACHA_RATE` で、かつ自分以外に利用中のセッションがあれば、その中から `random()` で 1 つ選び `delivered_session_id` にする。そうでなければ自分のセッションにする
- `GACHA_RATE` は環境変数（0〜1、既定 0.1）。E2E では 0 か 1 にして結果を固定する
- キッチン画面のカードには「→ 席 X へお届け（ガチャ）」と表示する

### WebSocket（`GET /ws`、パスは 1 本）

ブラウザの WebSocket はヘッダーを付けられず、URL のトークンはログに残りやすい。そのため**接続後の最初のメッセージで認証**する。

クライアント → サーバー（`ClientMessageSchema`）

| type | 中身 | 意味 |
|---|---|---|
| `auth` | `{ role: 'customer', sessionToken }` または `{ role: 'staff', staffKey }` | 認証。成功したら `staff` チャンネル、または `session:<id>` チャンネルを購読する |

サーバー → クライアント（`ServerMessageSchema`）

| type | 宛先 | 中身 | 発生するとき |
|---|---|---|---|
| `auth.ok` | 本人 | `{ role }` | 認証に成功した |
| `order.created` | staff | `{ order }` | 客が注文した |
| `order.updated` | staff、注文したセッション | `{ order }` | 状態の変更（キャンセルを含む） |
| `gift.received` | 届いた先のセッション | `{ order }` | ガチャで別の席に届いた |
| `session.started` | staff | `{ session: StaffSession }` | 新しい来店 |
| `session.closed` | staff、そのセッション | `{ sessionId }` | 会計済 |

- 認証に失敗したら close code `4001`、5 秒以内に `auth` が来なければ `4000`、形式が不正なメッセージは `4002` で切る
- 利用中でないセッションは認証できない。会計済になったら、そのセッションの接続を `session.closed` を送ってから切る
- 再接続（frontend）: 切断したら 1s, 2s, 4s … 最大 30s の間隔で再接続する。つながったら `auth` を送り、REST で一覧を取り直す。close code が `4001` のとき（認証失敗）は再接続しない

### 環境変数（`config.ts` で Zod 検証、`.env.example` だけをコミットする）

| 変数 | 既定 | 検証 |
|---|---|---|
| `PORT` | 3000 | 整数 |
| `DB_PATH` | `data/vibe-order.db` | 文字列 |
| `STAFF_KEY` | **なし（必須）** | 16 文字以上。無ければ起動しない |
| `SEAT_COUNT` | 20 | 1〜10000 の整数 |
| `GACHA_RATE` | 0.1 | 0〜1 |

## 5. 実装タスク（各 30 分以内、TDD）

各タスクは Red → Green → Refactor で進め、最後に `npm run check` と `npm run test` を通す。
**S を先に終えれば、B と F は並行して進められる。** F は B が終わるまで、api/client と WS をテスト用の偽物に差し替えて進める。

### Iteration 0: 準備

- `ws` と `@types/ws` の版、ライセンス、公開日を確認して memo.md に記録する（7 日ルール）
- `node:sqlite` の Node 公式ドキュメントを `docs/ref/` に保存する
- **受け入れ条件**: memo.md に記録がある。`npm audit` が 0 件

### shared（S）

| # | タスク | 受け入れ条件（テストで確認する） |
|---|---|---|
| S1 | `errors.ts`、`menu.ts` | 正しい MenuItem が通る。price が負、または soldOut が真偽値でないと失敗する。不明な error code は失敗する |
| S2 | `order.ts` のスキーマ | quantity が 0 / 11 / 1.5 だと失敗する。items が 0 件 / 21 件だと失敗する。menuId の重複は失敗する。status は 4 つの値以外は失敗する。`UpdateOrderStatusRequest` で `received` / `cancelled` は失敗する |
| S3 | `orderRules.ts` | `canTransition` は received→cooking、cooking→served だけが true（全 16 通りを表で検証）。`canCancel` は received だけ true。`orderTotal` が Σ単価×数量。`sessionTotal` は cancelled を除く |
| S4 | `session.ts`、`ws.ts` | 各メッセージの代表例が通る。`type` が不明だと失敗する。`auth` で role と認証情報の組み合わせが合わないと失敗する |

### backend（B）

| # | タスク | 受け入れ条件 |
|---|---|---|
| B1 | `config.ts` | STAFF_KEY が無い / 15 文字だと例外。既定値が入る。SEAT_COUNT=0 / GACHA_RATE=1.5 は例外 |
| B2 | `db/`（migrate と seed） | `:memory:` で migrate と seed のあと、menu が 10 件、売切れが 1 件、seats が SEAT_COUNT 件、トークンはすべて異なり 22 文字。2 回実行しても件数が変わらない。同じ席に利用中のセッションを 2 つ入れると制約違反になる |
| B3 | `GET /api/menu` | 200 で `MenuItem[]` のスキーマに合い、sort_order 順 |
| B4 | `POST /api/seats/:seatToken/session` | 初回は 201 で新しいセッション。同じ席の 2 回目は 200 で同じ sessionToken。会計済のあとは別の sessionToken。不明な席トークンは 404。新しい来店のとき Hub に `session.started` が出る |
| B5 | Session 認証と `GET /api/session` | トークンが無い / 不明は 401。会計済は 410。orders と gifts と total が返る。前の来店の注文は含まれない（同じ席で セッション1 で注文 → 会計済 → セッション2 では orders が空） |
| B6 | `POST /api/session/orders` | 201 で status = received、total が正しい。order_items に注文時の名前と単価が残る。売切れを含むと 409 で、注文は 1 件も作られない（トランザクション）。不明な menuId は 404。Hub に `order.created` が出る |
| B7 | キャンセル | received なら 200 で cancelled。cooking / served / cancelled なら 409。他のセッションの注文は 404。Hub の staff と注文したセッションに `order.updated` が出る |
| B8 | スタッフ認証と `GET /api/staff/orders` | キーが無い / 違うと 401。既定では received と cooking だけ、古い順。`status=served` で絞り込める。不正な status は 400 |
| B9 | `PATCH .../status` とガチャ | received→cooking、cooking→served は 200。それ以外は 409。served のとき: random を 0.99 に固定すると自分の席に届く。0.0 に固定し、他に利用中の席があれば別の席に届く（`delivery.isGacha = true`）。他に利用中の席が無ければ自分の席。届いた先のセッションに `gift.received` が出る |
| B10 | セッション一覧と会計済 | 利用中だけ返り、total と unfinishedCount が正しい。未完了の注文があると 409。会計済にすると ended_at が入り、以後そのトークンでの操作は 410。`session.closed` が出る |
| B11 | `GET /api/staff/seats` | SEAT_COUNT 件、label 順。キーが無いと 401 |
| B12 | `ws/hub.ts` | subscribe / unsubscribe / publish の単体テスト。チャンネルの購読者だけに届く。送信に失敗した購読者は外される |
| B13 | `ws/handler.ts` と `index.ts` の接続 | 結合テスト（`serve` をポート 0 で起動し、Node 標準の WebSocket で接続）: 正しい auth で `auth.ok`。キーが違うと 4001。5 秒 auth が無いと 4000（タイマーは注入して短くする）。客 A の注文が staff に届き、客 B には届かない |
| B14 | 非機能の確認 | 20 席ぶんの客の WS と staff の WS を接続した状態で、注文と状態変更のイベントが該当する接続に 1 秒以内に届く。REST の各 API が 1 秒以内に応答する |

### frontend（F）

frontend のユニットテストは、雛形と同じく `renderToString` と純粋関数で書く。クリックなどの操作は E2E で確かめる。

| # | タスク | 受け入れ条件 |
|---|---|---|
| F1 | 画面の切り替えと Vite の proxy | `App` に `/s/abc` を渡すと客の画面、`/kitchen` でキッチン画面、それ以外は NotFound を描画する（pathname を props で注入）。`vite.config.ts` の `server.proxy` と `preview.proxy` に `/api` と `/ws`（`ws: true`）がある |
| F2 | `api/client.ts` | 偽の fetch で: 成功した応答はスキーマで検証して返す。スキーマに合わない応答は例外。エラー応答は `code` を持つ `ApiError` になる。`X-Session-Token` / `X-Staff-Key` が付く |
| F3 | `ws/reconnectingSocket.ts` | 偽の WebSocket と偽のタイマーで: open で auth を送る。切断で 1s, 2s, 4s … 30s の間隔で再接続し、成功したら間隔を戻す。再接続したら `onReconnect` を呼ぶ（REST の取り直しに使う）。4001 では再接続しない。`ServerMessageSchema` に合わないメッセージは捨てる |

#### E2E での保護の扱い（保護を外さずにテストする）

- テスト用の `STAFF_KEY` を `webServer` の環境変数で渡す。同じ値を Playwright 側の環境変数からも読む（値はテスト専用の固定値で、本番のキーとは別）
- 席トークンは推測できないが、テストでは `request.get('/api/staff/seats', { headers: { 'X-Staff-Key': ... } })` で取得し、`/s/<token>` を開く。DB は毎回作り直すので、トークンも毎回変わる
- キッチン画面は `StaffKeyForm` にキーを入力して開く（シナリオ①で入力操作も確かめる）。ほかのシナリオでは `page.addInitScript` で sessionStorage にキーを入れて省略する
- 客ごとに別の `browser.newContext()` を使う。localStorage が分かれるので、2 つの席や 2 台のケータイを同時に再現できる
- 共通の処理は `e2e/fixtures.ts`（席 URL の取得、キッチン画面を開く）にまとめる
- テスト用のバイパス（認証を切るフラグなど）は作らない。本番と同じ経路で確かめるため

## 6. セキュリティ上の判断と残るリスク

- 秘密情報は `STAFF_KEY` だけ。`.env` はコミットせず、`.env.example`（値は空）だけを置く
- SQL はすべてプレースホルダ付きの prepared statement で書く（文字列の連結はしない）
- React の既定のエスケープに任せ、`dangerouslySetInnerHTML` は使わない
- **残るリスク（MVP では受け入れる）**
  - 席の QR の URL を持ち帰った人は、その席の次の来店に入れる。対策は将来の拡張（スタッフが来店を開始する、来店ごとの PIN など）
  - `STAFF_KEY` は全スタッフで共有する固定のキー。拡張のスタッフ認証（JWT）で置き換える
  - 回数の制限（rate limit）は無い。Codespaces のポートを Private / Organization にすることが前提

## 7. 将来の拡張（MVP の範囲外）

| 拡張 | 設計の方向性 |
|---|---|
| 席の状態管理（空席 / 着席 / 注文中 / 調理中 / 提供済 / 会計待ち） | 着席・会計待ちは sessions に列を足し、注文中〜提供済はセッション内の注文の状態から計算する。`seat.updated` イベントを追加する |
