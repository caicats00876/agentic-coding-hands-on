# Vibe Order（Codespaces 版）

リアルタイム オーダー管理システム

> 書籍 PART6 の要求仕様をもとに、研修用に範囲を絞り、AWS を使わず GitHub Codespaces 上で動く構成に置き換えたものです。
> 「MVP」は研修で必ず作る範囲、「拡張」は時間が余った人の追加課題です。

## 基本コンセプト

席ごとの注文を管理し、ホールとキッチンの情報共有を効率化する。
リアルタイム更新により、注文状況・調理進捗を即座に反映。

---

## コア機能

見出しの「（MVP）」は、**必ず作る範囲**という意味です（MVP = Minimum Viable Product、最小限の製品）。

### 1. オーダー管理（MVP）

- 席を選ぶとメニューを表示し、品目・数量を選択して注文できる
- 席ごとの注文履歴を一覧表示できる
- 注文のキャンセル（状態が「受付」のときのみ）

### 2. ステータス管理（MVP）

- 注文の状態
  - 受付 → 調理中 → 提供済（この順にのみ遷移できる）
- キッチン画面で注文の状態を変更できる

### 3. メニュー（MVP）

- メニューは初期データ（seed）で10品程度を登録する
  - 項目: 名前、価格、説明文、カテゴリ、売切れフラグ
- 売切れのメニューは注文できない

### 4. リアルタイム通知（MVP）

- 新規注文をキッチン画面に即時表示する
- 注文の状態変更を、該当する席の画面に即時反映する
- WebSocket による双方向通信
- WebSocket 切断時は自動で再接続する

### 5. 拡張課題

- 席の状態管理（空席 / 着席 / 注文中 / 調理中 / 提供済 / 会計待ち）
- 再注文機能
- メニューの CRUD 画面、おすすめフラグ
- スタッフ認証（固定ユーザー + JWT）とスタッフの状態（対応可能 / 対応中 / 休憩中）
- 注文オプション（大盛り、辛さなど）

## 技術スタック

- モノレポ: npm workspaces（packages/shared, packages/backend, packages/frontend）
- 共有スキーマ: Zod（packages/shared）
- バックエンド: Hono + @hono/node-server
- リアルタイム通信: WebSocket（Hono の Node.js 向け WebSocket ヘルパー）
- データストア: SQLite（テーブル: Menu / Orders。拡張で Seats / Staff）
- フロントエンド: React + TypeScript + Vite + Tailwind CSS
- 実行環境: GitHub Codespaces（ポート転送で公開）
- CI: GitHub Actions

---

## セキュリティ要件

- すべての API 入力を Zod でバリデーションする
- 秘密情報はコードに書かず、環境変数で渡す（`.env` はコミットしない）
- Codespaces のポート公開は「Private」または「Organization」とし、「Public」にしない

---

## 非機能要件

- レスポンスタイム: 1秒以内
- 同時接続数: 20席まで対応
- テストカバレッジ: 80%以上

## 決定事項

受講者が決めたことと、設計の質問への回答で決まったこと（2026-10-23）。詳しくは [システム設計](design/system-design.md) を参照。

- 「即時」とは: リロードしなくても画面が更新されること
- 席の数: 20（環境変数 `SEAT_COUNT` で変える。非機能要件の 20 席で検証する）
- 客の端末: 客が自分のケータイで注文する。どの席かは QR コードで識別する
- 研修での確認: 客の画面も PC のブラウザで動けば十分とする。QR の URL をブラウザで直接開いて確かめる。Codespaces のポートは Private なので、ケータイからの接続は確かめない
- 注文の単位: 1 回の注文に複数の品目を含められる。状態の変更とキャンセルは注文ごとに行う
- 画面の分担: キッチン画面は調理担当から配膳担当へ引き継いで使う。画面は 1 つで、受付 → 調理中 → 提供済 のすべてを操作する。調理担当と配膳担当の分担は運用で行う
- セッション: 席ごとに来店セッションを設け、同じ席でも前後の客の注文と会計を混ぜない
  - QR を読んだとき、その席に利用中のセッションが無ければ新しく作る
  - 同じ席の複数の端末は、同じセッションを共有する
  - キッチン画面の「会計済」でセッションを終える。終わったセッションでは注文できない
- 席トークンとスタッフキー
  - QR の URL には、推測できない席トークンを入れる（席の番号だけの URL にはしない）
  - キッチン用の API と WebSocket には、環境変数 `STAFF_KEY` と一致するスタッフキーが必要
- 注文ガチャ（MVP に含める）: たまに他の客が注文した商品が届く
  - 「提供済」にするとき、サーバーが一定の確率（環境変数 `GACHA_RATE`、既定 10%）で抽選する
  - 当たったら、利用中の別の席に届ける。キッチン画面には届け先の席を表示する
  - 代金は、注文した席の会計に残す
- 客の進捗画面
  - 客の画面に、自分の注文の進捗（受付 → 調理中 → 提供済）を表示する
  - 自分の席に届いたら、進捗の最後に「お待たせしました」を表示する
  - 他の席に届いたら（ガチャ）、進捗の最後に「残念」を表示する
  - 届いた側の席には「おすそ分けが届きました」を表示する
