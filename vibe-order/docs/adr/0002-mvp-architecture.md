# 2. vibe-order MVP のアーキテクチャ（来店セッション、node:sqlite、WebSocket）

## Status

Accepted（2026-10-23）

## Context

- `docs/requirements.md` の MVP として、注文、状態の管理（受付 → 調理中 → 提供済）、メニュー（seed）、WebSocket による即時の反映を作る
- 受講者が決めたこと
  - 客は自分のケータイで QR を読んで注文する
  - 「即時」とは、リロードしなくても画面が更新されること
  - 席の数は決め打ちにしない（10 でも 10000 でもよい）
  - 調理担当から配膳担当へ渡す流れがある
  - 注文ガチャ: たまに他の客が注文した商品が届く
- 2026-10-23 の設計の打ち合わせで、次の要望が出た
  - 同じ席でも、前後の客の注文と会計が混ざらないようにする
  - 客の画面に注文の進捗を出し、最後に「お待たせしました」または「残念」を表示する
- MVP にはスタッフ認証が無い。席の番号だけの URL では、他の席になりすまして注文できる。客がキッチンの操作をすることもできてしまう
- プロジェクトルール: セキュリティを最優先、KISS、依存は最小限、TDD、カバレッジ 80% 以上
- 雛形（ADR 0001）: npm workspaces（shared / backend / frontend）、Hono + @hono/node-server 2.1.5、React + Vite、Vitest、Playwright、Node 24

## Decision

1. **shared を契約にする。** Zod スキーマと純粋関数を shared に置き、それを先に実装する
   - 純粋関数: 状態遷移の判定、合計金額の計算
   - shared が終われば、backend と frontend を別々に並行して実装できる
2. **注文の単位**: 1 注文 = 複数の品目（`orders` + `order_items`）。状態とキャンセルは注文ごとに扱う。`order_items` には注文した時点の名前と単価を残す
3. **状態**: `received` → `cooking` → `served` の順にだけ進める。キャンセル（`cancelled`）は `received` のときだけできる。キッチン画面は 1 つで、すべての遷移を操作する
4. **来店セッション**: `sessions` テーブルを設ける
   - QR を読んだとき、その席に利用中のセッションが無ければ作る
   - 同じ席の複数のケータイは、同じセッションを共有する
   - スタッフの「会計済」でセッションを終える。未完了の注文が残っている間は終えられない
   - 1 つの席で利用中のセッションは 1 つだけにする（部分 UNIQUE インデックス）
5. **保護**
   - QR の URL には推測できない席トークン（16 バイトの乱数）を入れる
   - 客の API はセッショントークン（`X-Session-Token`）で認証する
   - スタッフの API は `X-Staff-Key` を環境変数 `STAFF_KEY` と定数時間で比べる
   - WebSocket は、接続したあと最初のメッセージで認証する
6. **注文ガチャを MVP に入れる**
   - `served` にするとき、サーバーが確率 `GACHA_RATE`（既定 0.1）で抽選する
   - 当たったら、利用中の別のセッションに届け先（`delivered_session_id`）を変える
   - 代金は、注文したセッションの会計に残す
7. **データストア**: Node 24 標準の `node:sqlite` を使う。テーブルは `STRICT` にする
8. **WebSocket**: `@hono/node-server` の `upgradeWebSocket` と `ws` を使い、`/ws` の 1 本にする
   - 購読のチャンネルは `staff` と `session:<id>` に分ける
   - イベントには注文 DTO の全体を載せる
   - 再接続したら、REST で一覧を取り直す
9. **配信**: Vite の proxy で `/api` と `/ws` を同じオリジンにまとめる。CORS の設定はしない
10. **E2E**: 認証を外すフラグは作らない。テスト用の `STAFF_KEY` で席トークンを取得し、本番と同じ経路でテストする

## Consequences

- 良い点
  - 前後の来店の注文と会計が、データ構造の上で分かれる
  - 他の席になりすまして注文すること、客がキッチンを操作することを防げる
  - shared の契約が先に決まるので、backend と frontend を並行して開発できる
  - SQLite の依存を増やさずに済む。新しく増える依存は `ws` と `@types/ws` だけ
  - 乱数と時刻を注入するので、ガチャと時間に関わる処理を決まった結果でテストできる
- 悪い点・注意点
  - 席の QR の URL を持ち帰った人は、その席の次の来店に入れる。MVP では受け入れ、将来の拡張で対策する（スタッフが来店を開始する方式、来店ごとの PIN など）
  - `STAFF_KEY` は全スタッフで共有する固定のキーである。拡張の JWT 認証で置き換える
  - 回数の制限（rate limit）が無い。Codespaces のポートを Private / Organization にすることが前提になる
  - QR 画像は MVP では作らない。スタッフ画面の URL から、外部のツールで作る
  - 研修では、客の画面も PC のブラウザで QR の URL を直接開いて確かめる。ケータイの実機からの接続は確かめない（Codespaces のポートは Private のため）
  - `node:sqlite` は同期 API である。20 席の規模なら問題ないが、大きな規模では見直しが要る
  - frontend のユニットテストは `renderToString` と純粋関数だけで書く。操作の確認は E2E に頼る
