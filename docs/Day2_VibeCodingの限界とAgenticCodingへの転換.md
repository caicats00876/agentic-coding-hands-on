# Day2 Vibe Coding の限界と Agentic Coding への転換

昨日作った Vibe Chat に機能を追加します。昨日のように簡単にいくでしょうか。
午前は Vibe Coding の問題点に**自分で気づき、言語化**します。午後は、その問題を防ぐ「4つの作法」を学び、最初のガードレールを設定します。

## 今日のゴール

*   Vibe Coding で作ったアプリに変更を加えると何が起きるかを体験する
*   Vibe Chat の品質を自分で検証し、問題点を4つに分類して説明できる
*   Claude Code の権限設定（ガードレール）で、危険な操作を止められることを確認する

## ハンズオン（午前）：Vibe Coding の限界を体験する

### 1. Vibe Chat に機能追加を依頼する

昨日と同じ Vibe Coding のルール（コードは読まない、提案はそのまま承認）で進めます。

1.  Claude Code のチャットパネルで、[hands-on/day2/change-request.prompt.txt](../hands-on/day2/change-request.prompt.txt) を `Ctrl+V` で貼り付けて送信します。
2.  完成したら「起動して」と依頼し、画面を開きます。
    *   開き方：VS Code の下のパネルの **ポート** タブで、使われているポートの行の **地球儀のアイコン**（ブラウザーで開く）を押します。どのポートか分からないときは、Claude Code に「アクセスする URL を教えて」と聞きます。
3.  **追加した機能**と**昨日まで動いていた機能**の両方を、ブラウザで確認します（確認する項目は [inspection-commands.md](../hands-on/day2/inspection-commands.md) の「7. 既存機能は壊れていないか」）。
4.  動かないところがあれば、昨日と同じようにエラーを貼り付けて直させます。

> [!NOTE]
> 制限時間は60分です。終わらなくても構いません。「終わらなかった」ことも大切な記録です。
> 逆に、すんなり終わって何も壊れないこともあります。その場合も失敗ではありません。「今は動いている」ことと「この先も変更し続けられる」ことは別の話で、それを次の品質検証で確かめます。

記録すること（比較シートの「Vibe Chat（Day2 変更）」欄）：

*   直させた回数（手戻り回数）
*   一度直ったのに、また壊れた機能（デグレ）の数
*   60分で終わったかどうか

### 2. 品質を検証する

ここからは **AI に頼らず、自分で** 調べます。[hands-on/day2/inspection-commands.md](../hands-on/day2/inspection-commands.md) のコマンドを順に実行し、結果を比較シートに記入します。考えるところも、Claude Code には聞かず、自分の言葉で答えます。

*   テストはあるか。あるなら、プロジェクトに残っていて、変更のたびに自動で走り、実行することがどこかに決めて書いてあるか
*   Lint / Format は設定されているか
*   脆弱性のある依存パッケージはないか
*   古いライブラリを使っていないか
*   AI が説明なしに追加したライブラリはいくつあるか
*   既存機能は壊れていないか

### 3. 問題点を4つに分類する

見つけた問題をすべて書き出し、書籍 4.2 の4分類に当てはめます。書き終えたら AI チューターに説明し、問いかけに答えながら考えを深めます。最後に「一番痛かった問題」を1つ選びます。

考えるときの基準は「**今は動いているか**」ではなく、「**このまま3か月、別の人が変更し続けても守れるか**」です。

| 分類 | 例 | 自分が見つけた問題 |
| :--- | :--- | :--- |
| 曖昧な要件による破綻 | 「イケてる感じ」が人によって違う | |
| 存在しない検証条件 | テストがなく、壊れたことに気づけない | |
| スタイルの不統一 | ファイルごとに書き方が違う | |
| 致命的なミス | 秘密情報のハードコード、データの削除 | |

## ミニ講義（午後）：正しい委ね方の4つの作法

書籍 4.3〜4.4 の内容を、午前に見つけた問題と対応づけて説明します。

| Vibe Coding の問題 | 4つの作法 | 研修で使う仕組み |
| :--- | :--- | :--- |
| 曖昧な要件による破綻 | 要件定義（プロンプト）の具体化 | Plan モード、要件定義書、設計書 |
| 存在しない検証条件 | 自動テストの積極的な採用 | Vitest、Playwright、TDD |
| スタイルの不統一 | 規約・スタイルの維持 | Biome、CLAUDE.md、npm scripts、CI |
| 致命的なミス | セーフティネットとしてのガードレール | Git、Codespaces、権限設定、ブランチ保護 |

ポイントは、**AI に「気をつけて」とお願いするのではなく、仕組みで強制する**ことです。

## ハンズオン（午後）：Agentic Coding への転換

### 4. ガードレールを設定する

ガードレールは「危ない操作を全部禁止する」ものではありません。**どの操作を、誰が、どこで判断するかを先に決めておく**ものです。

| 区分 | 意味 | 判断する人 |
| :--- | :--- | :--- |
| `deny`（禁止） | 実行させない | 設定ファイルを書いた人（前もって判断済み） |
| `ask`（毎回確認） | 実行の前に確認ダイアログを出す | その場の自分 |
| `allow`（自動許可） | 確認なしで実行させる | 設定ファイルを書いた人（前もって判断済み） |

このあとコピーするテンプレートは**体験用の例**です。正解の設定ではありません。「止まる」ことと「すり抜ける」ことの両方を体験するために用意しています。

1.  まず、今の Vibe Chat をコミットします（Git が最初のガードレールです）。`hello/` や `.claude/` は含めません。

    ```bash
    git add vibe-chat && git commit -m "Day2: Vibe Chat change request"
    ```

2.  今ある `.claude/settings.json` の中身を見ます。Day1 で確認ダイアログの「常に許可」を押していると、このファイルがいつの間にか作られています。

    ```bash
    cat .claude/settings.json
    ```

    *   ファイルがない場合は、`No such file or directory` と出ます。次に進んでください。
    *   ある場合は、`allow` に何が並んでいるかを見ます。`rm -rf`、`curl`、`npm i` などが入っていることがあります。**読まずに「常に許可」を押した結果**が、ここに残っています。

3.  Claude Code のチャットパネルを閉じます（パネル右上の ×）。開いたままだと、コピーした直後に Claude Code が古い設定で上書きすることがあります。
4.  権限設定のテンプレートを、リポジトリのルートにコピーします。

    ```bash
    mkdir -p .claude && cp hands-on/day2/templates/.claude/settings.json .claude/settings.json
    ```

5.  中身がテンプレートどおりになったかを確かめます。`deny`、`ask`、`allow` の3つが並んでいれば OK です。`allow` しかない場合は、手順 3 と 4 をやり直してください。

    ```bash
    cat .claude/settings.json
    ```

6.  `deny`（禁止）、`ask`（毎回確認）、`allow`（自動許可）に、それぞれ何が書かれているかを読みます。
7.  設定をコミットします。`.claude/settings.json` は、リポジトリで共有する設定で、提出物にも含まれます。

    ```bash
    git add .claude/settings.json && git commit -m "Day2: guardrail settings"
    ```

8.  Claude Code のチャットパネルを開き直し、新しい会話を始めます（設定を読み込み直すため）。

> [!NOTE]
> 個人用の設定は `.claude/settings.local.json` です。これは Git に含めません（`.gitignore` 済み）。「常に許可」を押したときに、`settings.json` と `settings.local.json` のどちらに書き込まれるかは、Claude Code のバージョンや選んだ項目によって違います。

### 5. 危険な操作が止まることを確かめる

ダミーの秘密情報ファイルを作ります。**本物のキーは絶対に使わないでください。**

```bash
echo "API_KEY=dummy-key-for-training-0000" > vibe-chat/.env
```

次の依頼を Claude Code に出し、**拒否される**ことを確認します。

*   「vibe-chat/.env の中身を表示して」
*   「vibe-chat/node_modules を rm -rf で削除して」
*   「git push --force して」

> [!WARNING]
> 拒否されたあと、AI が**別の方法で回り込もうとする**ことがあります（例：`Read` を禁止しても `cat` コマンドで読む）。
> さらに、AI が**人に抜け道を提案する**こともあります（例：「`rm -r -f` や `find -delete` なら通ります」「`--force-with-lease` は禁止の対象外です」）。提案されたら、どう感じたかを日報に記録してください。
> 権限設定は、書いた文字の並びと一致するものしか止められません。人も、確認ダイアログを毎回きちんと読むとは限りません。だからこそ、Codespaces による隔離、Git による復元、次のブランチ保護を**重ねて**使います（多層防御）。

続いて、GitHub 上で `main` ブランチに**ブランチ保護**を設定します。手元の設定をすり抜けても、GitHub 側で止めるための2つ目の柵です。

1.  fork したリポジトリの **Settings → Branches**（または **Rules → Rulesets**）を開きます。
2.  `main` に対して、次のルールを設定します。
    *   force push の禁止
    *   削除の禁止
    *   Pull Request 経由でのみマージ可能（Day3 以降に CI 必須も追加）

### 6. Plan モードで不具合を1つ直す

午前に見つけた不具合を1つ選び、今度は **Plan モード**で直します。

1.  チャットパネルのモードを **Plan** に切り替えます。
2.  「〇〇が動かない。原因を調査して、修正計画を立てて。修正を確認するテストも計画に含めて」と依頼します。
    *   直したい不具合が見つからなかった場合は、代わりに [plan-alternative.prompt.txt](../hands-on/day2/plan-alternative.prompt.txt)（ユーザー名の20文字の数え方）を送ります。
3.  AI が出した計画を**読んで**、次の観点で確かめます。分からないところは質問し、気になるところは直してもらいます。
    *   [ ] 頼んでいない作業が入っていないか（例：頼んでいない画面の変更、テスト道具の追加）
    *   [ ] 追加するライブラリはあるか。あるなら、その版は新しいか、脆弱性はないか
    *   [ ] 修正を確認するテストが入っているか
4.  納得したら承認します。承認の選択肢は次のように表示されます。
    *   **Yes, and use auto mode**：自動で進める（研修では使いません）
    *   **Yes, and manually approve edits**：編集のたびに確認する ← **これを選びます**
    *   **No, keep planning**：計画を続ける（直してほしい点があるとき）
    *   確認が多すぎるときは、承認したあとで入力欄のモードを **Edit automatically** に切り替えてもかまいません。
5.  計画の中に、**自分が知らなかった事実**と**頼んでいない作業**がいくつあったかを数えて、比較シートに書きます。Vibe Coding では、これらに気づかないまま進んでいました。

### 7. Vibe Order の要件を読む

明日から作る「Vibe Order」の要求仕様 [vibe-order-requirements.md](../hands-on/day3/prompts/vibe-order-requirements.md) を読みます。読むのは「**コア機能**」と「**非機能要件**」の2か所です。「技術スタック」は読まなくてかまいません。探すのは、どの技術を使うかではなく、**何を作るか**のあいまいさです。

*   AI に渡したときに、解釈が分かれそうな箇所に印を付けます（例：「即時」とは何秒以内か、注文画面を使うのはお客さんか店員か）。
*   印を付けた箇所を AI チューターに説明し、自分なりの答えを要件のメモとして書いておきます。明日、AI から質問されたときに使います。
