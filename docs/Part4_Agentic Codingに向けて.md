# PART 4 Agentic Codingに向けて

PART3ではVibe Codingを通じて、Coding Agentがわずか数時間でチャットアプリケーションを構築する過程を体験しました。しかし、あのような作り方をした成果物は、そのままプロダクション環境に持ち込んで通用するのでしょうか。このPARTでは一度立ち止まり、PART3の成果物を客観的に検証して起きたことを振り返り、プロダクション品質を実現するために人間が整えるべきことを明らかにします。

## 4.1 Vibe Codingの振り返り

前PARTのVibe Codingで作成した「Vibe Chat」について検証してみましょう。Vibe Codingとは、コードの存在すら忘れて、使い捨てプロジェクトを楽しく構築することです。これは、責任あるプロダクションコード構築プロセスの一環としてLLMツールを使用することとは異なります。

### 4.1.1 Vibe Codingの結果確認
「Vibe Chat」プロジェクトの状態を確認してみると、以下のような課題が見つかります。

*   **テストコードが書かれていない**: タスクランナーに `"test": "npm run test --workspaces"` と書かれているものの、実際に動かすとテストコードが存在しない旨が表示されます。
*   **Unitテストだけでなく、E2Eテストもないため動作検証ができない**: 場当たり的な改修になり時間がかかります。
*   **Formatter/Linterについても、同様に設定されていない**。
*   **新規開発にも関わらず、明らかに古いライブラリを採用している**: 物によってはバージョン切れのものを気にせず利用しています。
*   **説明せずに多数のライブラリを利用している**: サプライチェーン攻撃のリスクがあります。

実際にESLintやnpm audit、Trivyといったツールでセキュリティやコード品質について確認したところ、少なからず問題（脆弱性やエラー）があることが分かりました。

### 4.1.2 Simon Willison氏の指摘の検証
検証結果から、以下の違いがあることが分かります。

| 項目 | Vibe Codingの成果物 | プロダクションコード |
| :--- | :--- | :--- |
| **開発速度** | 非常に高速（2〜3時間） | 一般的な時間（数週間〜数ヶ月） |
| **コード品質** | プロトタイプ | 高品質 |
| **テストカバレッジ** | ほぼ0% | 80%以上 |
| **セキュリティ** | 基本的対策のみ | 包括的対策 |
| **保守性** | 低い | 高い |

すなわちVibe Codingは、新規ビジネスのアイデア検証や市場性確認など、割り切った実装で素早く形にする「プロトタイピング」に適した開発スタイルと言えます。

### 4.1.3 Coding Agentはプロトタイピング専用なのか
PART3でのVibe CodingではCoding Agentの練習も兼ねていました。エージェントの速度や性能について実感をもって知ることができた反面、エージェントへ全てを委ねる限界も理解できたでしょう。もっとエージェントとペアプログラミング方式で進めたのならば、どれだけエージェントの力を引き出せるでしょうか。

## 4.2 Coding Agentに委ねたときに起こること

Vibe Codingを経験すると、エージェントの能力が時として「ちぐはぐ」に感じられることがあります。実装速度は速く、基本的なコーディングが十分にできているように見えるのに、実際に動かすとエラーがあり、人間がフォローする部分は少なくありません。

### 4.2.1 曖昧な要件による破綻
ユーザーが与えた要件や指示（プロンプト）が曖昧だと、手戻りの多い実装を生み出します。意図を汲み取れずにその場しのぎのスタイルになったり、ゴールに向けた認識合わせが失敗しているように見えます。

### 4.2.2 存在しない検証条件
Vibe Codingでは実現したい完成形のイメージを伝えるだけで実装を始められます。しかし、「この程度の確認で十分だろう」と済まされてしまったような部分もあるでしょう。人間を介した検証フェーズが全体のボトルネックとなり、開発速度は想定よりも向上しないこともあります。

### 4.2.3 スタイルの不統一
特定のエージェントにプロンプトを実行し続けていると、優秀な特定個人がチームに入ったような感覚になります。しかし、ソースコードのスタイルが不統一な状態（コメントのスタイルや関数の書き方がバラバラなど）になり、意図を理解するのに不要な時間を費やしてしまいます。

### 4.2.4 致命的なミス
エージェントに委ねることで、以下のような致命的なミスが発生するケースもあります。
*   `rm` コマンドで誤って、ユーザが意図しないローカルのデータを削除してしまう。
*   処理をいったん仕切り直す目的などで、データベースへ `DELETE` 文や `TRUNCATE` 文を実行し、テストデータを破壊してしまう。
*   開発者用の `.env` ファイルに含まれるAPIキーなどの機密情報をハードコードしたままコミット、あるいは外部へ送信してしまう。

## 4.3 正しい委ね方の作法

AIエージェントはシステム開発のソフトウェア開発で「当たり前」とされてきた開発者のためのベストプラクティスを、AI開発においても愚直に適用することが答えです。成功率を高める4つの「委ね方の作法」は以下の通りです。

### 4.3.1 要件定義（プロンプト）の具体化
ユーザーが与えた要件や指示（プロンプト）が曖昧であるのなら、具体的な明確にする工程を挟むのが効果的です。タスクの目的、仕様、制約を明確に定義します。エージェントに計画を立てさせ、実装の方向性を明確にする「プランモード」と呼ばれる機能が有効です。

### 4.3.2 自動テストの積極的な採用
手動の検証がボトルネックとなるのであれば、検証可能な要件を言語化し、自動テストに置き換えてチェック量を補います。検証基準を先にコードで定義し、自動テストを前提とした開発フロー（テスト駆動開発: TDD）を構築することで、検証作業を確実に高速化できます。

### 4.3.3 規約・スタイルの維持
生成されるコードの一貫性を保つために、プロジェクト固有のルールをできるだけ沢山エージェントに伝えたくなります。しかし、リンターやフォーマッターを組み込んだタスクランナーとCIパイプラインを整備し、コードスタイルや品質基準を自動的に強制する方が効果的です。

### 4.3.4 開発を支える4つのツールと仕組み
*   **リンター (Linter)**: コードの品質や構文をチェックするツール（例：ESLint, Biome）。
*   **フォーマッター (Formatter)**: コードの書式を自動的に統一するツール（例：Prettier, Biome）。
*   **タスクランナー (Task Runner)**: 複数のコマンドをまとめて実行する仕組み（例：`npm run test`）。
*   **CIパイプライン**: コードの変更時に自動的にテストやチェックを実行する仕組み（例：GitHub Actions）。

### 4.3.5 セーフティネットとしてのガードレール
致命的なミスを防ぐためには、エージェントの能力を最大限に引き出す前提での自由である必要があります。具体的にはバージョン管理、開発環境の隔離、権限管理などのような、ソフトウェアエンジニアリングで確立された多層的な防御策を講じることが重要です。

### 4.3.6 実践に向けて
明確な要件定義によってエージェントの実行精度が向上し、自動テストが生成されたコードを即座に検証します。また、リンターやフォーマッターがスタイルを自動的に矯正し、ガードレールが致命的なミスを未然に防ぎます。これらの概念が組み合わされることで、エージェントがコードを生成し、問題が自動的に検出され、エージェント自身が修正するという品質改善のサイクルが生まれます。

## 4.4 エージェントへのガードレール

AIエージェントと協働しながら品質と安全性を確保するための「ガードレール」の具体例を紹介します。

### 4.4.1 ガードレールの観点
*   **バージョン管理システムの導入**
*   **開発環境の隔離**
*   **権限管理**
*   **継続的インテグレーションの整備**

### 4.4.2 ガードレールの実例
*   **4.4.2.1 バージョン管理システムの導入**: 
    Gitなどのバージョン管理システムを利用し、コードの安全性を保ちます。ブランチ保護ルールを設け、強制的な上書き（force push）を禁止するなどの対策が有効です。
*   **4.4.2.2 開発環境の隔離**: 
    エージェントが誤って本番環境やテスト環境のデータを破壊しないよう、独立した仮想マシン、Dev Container、GitHub Codespacesなどのサンドボックス環境を整備します。
*   **4.4.2.3 権限管理**: 
    エージェントには「最小権限の原則」を適用し、不必要なファイル操作やクラウドインフラへのアクセス権を与えないようにします。
*   **4.4.2.4 継続的インテグレーションの整備**: 
    CI/CDパイプラインを構築し、エージェントがコードを生成するたびに自動的にビルドとテストが実行される環境を整えます。これにより、品質基準を自動的に強制できます。

## PART 4 Summary
PART4では、Coding Agentとの協働において発生しがちな問題と、それらに対する「正しい委ね方の作法」について解説しました。
エージェントに開発を委ねる際に見られる曖昧な要件、存在しない検証条件、スタイルの不統一、致命的なミスといった課題は、実は従来のソフトウェア開発で長年議論されてきた要因と同じです。人間主体の開発においても、これらは品質とスピードの両立を妨げてきました。
大切なのは、AIに過度の期待を寄せて基本的な開発プラクティスを軽視するのではなく、エージェントの特性を理解した上で、従来のベストプラクティスをより厳格に適用することです。
PART4で紹介した4つの作法（要件定義の具体化、自動テストの積極採用、規約・スタイルの維持、ガードレールの整備）は、Agentic Codingを成功に導くための基盤となります。
