# PART 6 Agentic Coding - コーディング

PART5では開発基盤としてモノレポ環境の構築とガードレールの整備を行いました[1, 2]。本PARTではいよいよ、Agentic Codingによるアプリケーション開発を実践します[1]。要求仕様の策定から設計、共通部分・バックエンド・フロントエンドの実装まで、エージェントとの対話を通じて段階的に進めるプロセスを紹介します[1]。

## 6.1 コーディングの進め方
本PARTではいよいよAgentic Codingとして、ソースコードや設定ファイルをエージェントと共に作成していきます[2]。基本的な進め方としては以下の順で進めます[2]。
1. コーディングルールの整備
2. 要求を元に要求設計を具体化
3. 共通部分の開発
4. バックエンド部分の開発
5. フロントエンド部分の開発

### 6.1.1 コーディングルールの整備
PART5と同じように作業用の新しいブランチを作成し、GitHub Codespacesを起動します[2]。コーディングに特化したルールを `coding.md` として新たに追加します[2]。既存コードベースの尊重、ライブラリ導入ルール、コード変更の箇所、E2Eテストのルール、フロントエンド/バックエンド連携などのルールを記載します[2]。

## 6.2 要求からの設計書作成
それではアプリケーションを設計していきましょう[3]。複雑な作業なので、今回も仕様駆動開発を実現する `/deep-planning` コマンドを軸に設計を進めます[3]。

### 6.2.1 要求仕様の作成
PART3ではチャットシステムを実装しましたが、今回は飲食店のオーダーシステム（Vibe Order）を作ります[3]。ホール担当者が席ごとの注文を登録し、キッチン担当者がリアルタイムで注文状況を確認できるシステムです[4]。
基本コンセプト、コア機能（オーダー管理、ステータス管理、メニュー管理など）、技術スタック、非機能要件などを定義したプロンプトをClineに渡します[4]。

### 6.2.2 Coding Agentへの設計依頼
`/deep-planning @/docs/design/system-design.md を前提に、モノレポ雛形を使って新しいシステムを開発します。` といったプロンプトで設計を依頼します[5]。
途中、Clineが実装方針（WebSocketの認証方式など）について選択肢を提示してくることがあります[5]。ユーザーが間違った選択肢を指示してしまっても、Clineの判断を仰ぎながら方向性を修正して進めることができます[6]。

### 6.2.3 設計ファイルの分割
作成された設計ファイル（`implementation_plan_vibe_order.md`）のサイズが大きすぎる場合、そのままではエージェントが扱いづらいため、`shared/`、`frontend/`、`backend/`、`aws/` などのパッケージごとに設計を分割する計画を立てさせます[7]。これにより、タスクの粒度が細かくなり管理しやすくなります[7]。

## 6.3 共通部分
設計ファイルの分割が完了したため、次は共通部分（`shared/`）の実装に進みます[8]。

### 6.3.1 共通部分の実装計画
作成した設計ドキュメントを参照しながらClineに実装計画を依頼します[8]。提示された計画に、時間配分やTDD（テスト駆動開発）準拠といった重要な観点が記載されているかを確認します[9]。

### 6.3.2 共通部分の実装
計画に問題がなければ、Actモードに切り替えて実装を開始します[9]。各イテレーションでテストカバレッジ100%を進めながら実装を行います[10]。
途中でLintエラーや型エラー、コマンド実行の失敗などが発生した場合は、ターミナルの出力結果を取得（「再試行」ボタンのクリックなど）してエージェントに自己修復させながら進めます[10]。

### 6.3.3 実装完了と品質確認
全ての実装が終わったら、`selfcheck` コマンドを使って品質を確認します[11]。Lintの警告や不足しているテストケースがないかをLLMに機械的にレビューさせ、問題があれば修正指示を出します[11]。最終的にテストカバレッジが目標を満たしているか確認します[11]。

## 6.4 バックエンド
今回のバックエンド開発では「Hono」を利用します[12]。

### 6.4.1 llms.txtの導入
Honoの知識をCoding Agentへ効率的に伝えるため、公式が公開しているLLM向けのメタデータファイル `llms.txt` をダウンロードしてローカルに配置し、プロンプトで参照させます[12]。これにより、最新の仕様に基づいた実装が可能になります[13]。

### 6.4.2 バックエンドの実装計画
`llms.txt` の内容と要件定義書をもとに実装計画を立てさせます[13]。Clineにアーキテクチャの選択肢を提示させ、最適なアプローチを選択します[13]。さらに、計画の弱点や観点の抜け漏れをCline自身に自己評価させ、改善点を洗い出してから実装計画を確定させます[14]。

### 6.4.3 バックエンドの実装
計画が確定したら、Actモードで実装を進めます[14]。依存関係のインストールや基盤となる部分の実装が行われます[14]。TypeScriptの型エラーなどに対しては、必要に応じてユーザーが改善指示を与えます[15]。
また、コンテキストウィンドウの使用率が高まってきた場合は、新しいタスクとして切り出す「コンテキストクリア」を行い、性能を維持します[15]。

### 6.4.4 実装完了と品質確認
作成されたタスクリストファイルを再開し、残りのイテレーションを完了させます[16]。実装内容を確認し、問題があれば修正を指示します[16]。人間側でもクロスチェックを行い、品質を担保します[16]。

## 6.5 フロントエンド
最後にフロントエンドの実装を行います[17]。UI構築用のライブラリ「React」、スタイル設計に用いる「Tailwind CSS」、ビルドを支える「Vite」などを利用します[17]。

### 6.5.1 llms.txtの導入
フロントエンドにおいても、Viteに関する `llms.txt` があるのでローカルにダウンロードしておきます[17]。

### 6.5.2 フロントエンドの実装計画
設計書と `llms.txt` をもとに実装計画を立てます[17]。使用するライブラリのバージョンを調べさせ、最新版を使用するように指示します[17]。

### 6.5.3 フロントエンドの実装
UIコンポーネントや各ページのレイアウトを実装します[18, 19]。コードの静的解析（Lint）とテストカバレッジを高い水準で維持しながら進めます[20]。
E2EテストではPlaywrightのモック機能を利用し、バックエンドがAWSにデプロイされる前の状況であっても、フロントエンド単体で正しく動作するか確認できる状態にします[21]。

### 6.5.4 実装完了と品質確認
E2Eテストを実行し、失敗した場合はClineにエラーメッセージを分析させてデバッグを行います[22]。最終的に全てのテストが合格することを確認します[22]。
バックエンドの時と同じように `selfcheck` コマンドでレビューを依頼し、定常的な観点を機械的に確認させます[22]。
