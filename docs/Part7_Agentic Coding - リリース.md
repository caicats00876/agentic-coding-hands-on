# PART 7 Agentic Coding - リリース

PART6では、Agentic Codingによるアプリケーション開発を実践しました。本PARTでは、開発したアプリケーションを実際にAWS環境にデプロイし、E2Eテストで品質を担保するまでの一連のリリースプロセスを紹介します。MCPサーバーを活用したインフラ開発から、CI/CDパイプラインの構築、デプロイ後の動作確認まで、エージェントと協働しながら進めていきます。

## 7.1 リリースの進め方
これまでのPARTではローカル環境での開発に焦点を当ててきましたが、実際のアプリケーション開発ではクラウド環境へのデプロイが必要です。リリースフェーズでも「4つの作法（要件定義の具体化、自動テストの積極的な採用、規約・スタイルの維持、セーフティネットとしてのガードレール）」は変わりません。特にインフラストラクチャのコード化においては、意図しない変更に対するガードレールの重要性がさらに高まります。

### 7.1.1 リリース用ルールの整備
アプリケーションコードの開発時と同様に、リリース用のルールを整備します。作業用の新しいブランチを作成し、GitHub Codespaces上で `.clinerules/infrastructure.md` というルールファイルを作成します。
このファイルには、AWSの知識は「AWS Knowledge MCP Server」から取得することや、インフラ環境は「AWS CDK V2 (TypeScript)」で管理すること、デプロイは段階的に行い `cdk diff` などで差分を確認することといったルールを記載し、Workspace Rulesとして有効化します。

## 7.2 MCPの設定
インフラ開発の能力を強化するために、AWSが公式提供する2つのMCPサーバーを設定します。

### 7.2.1 CDK開発を強化するMCPサーバー
*   **AWS Knowledge MCP Server**: 最新のAWSドキュメントやベストプラクティスを提供します。エージェントを通じて最新のAWS情報を基にしたインフラコードを生成できます。
*   **AWS CDK MCP Server**: CDK開発に特化したガイダンスを提供します。規範的なコードパターンや、`cdk-nag` を用いたセキュリティコンプライアンスチェックなどをサポートします。

### 7.2.2 uvの導入
今回導入する AWS CDK Server は、Pythonのパッケージマネージャである「uv」での実行が前提となります。そのため、Dev Container環境のターミナルで `pipx install uv` コマンドを実行し、事前にuvをインストールしておきます。

### 7.2.3 AWS Knowledge MCP Serverの設定
ClineのMCP Servers設定（歯車アイコン）を開き、「Configure」タブから設定を行います。`cline_mcp_settings.json` ファイルが自動で開かれるので、公式ドキュメントに従い、AWS Knowledge MCP ServerのエンドポイントURLなどを指定して保存します。

### 7.2.4 AWS CDK MCP Serverの設定
同様に、ローカルで動作する AWS CDK MCP Server も設定に追加します。設定完了後、ClineのMCP Servers画面で両方のサーバーが追加され、有効化（グリーンのアイコン点灯）されていることを確認します。

## 7.3 デプロイ環境の実装
準備が整ったら、Agentic CodingによるAWSインフラ開発を進めます。

### 7.3.1 実装計画の策定
Clineに `/deep-planning` コマンドを使って実装計画を立てさせます。要件定義書とパッケージ構成を読み込ませ、デプロイメントの戦略を検討させます。
ClineはAWS Knowledge MCP Serverを利用して最新情報を調べた上で、Lambda関数を個別に作成するアプローチや、Honoのアプリケーションを単一のLambda関数として統合するアプローチなど、複数の選択肢を提示してくれます。人間が要件に合ったアプローチ（今回はHono統合）を選択し、実装方針を確定させます。

### 7.3.2 デプロイ前の動作確認
各Stackの実装が完了したら、`cdk synth` コマンドを実行してCloudFormationテンプレートが正しく生成されるか確認します。
エラーが発生した場合は、ターミナルの出力（`@terminal`）をClineに読み込ませて解析・自己修復させます。また、`cdk-nag` によるセキュリティの警告（非推奨APIの使用や暗号化の欠如など）が出た場合も、優先度付きの修正タスクとしてClineに順番に対応させます。

## 7.4 デプロイ
ローカルでのデプロイ準備が整ったら、GitHub Actionsを用いてCI/CDパイプラインから安全にデプロイする環境を構築します。

### 7.4.1 CI/CD環境の設計
`/deep-planning` コマンドを活用し、CI/CD環境の設計を行います。デプロイのトリガー条件、AWS認証方法（OIDC推奨）、フロントエンドの配信方法（S3 + CloudFront）、デプロイ範囲などの選択肢をClineに確認させながら、確実なパイプライン設計書を作成します。

### 7.4.2 CI/CD環境の実装
設計書に基づき、Phaseごとに段階的に実装を進めます。AWS OIDCプロバイダーの作成やIAM Roleの準備、GitHub Actionsのワークフローファイル（`.github/workflows/deploy.yml`）の設定などをClineに任せます。

### 7.4.3 CI/CD環境の検証
CI/CD環境の実装が完了したら、`/selfcheck` コマンドでレビューを依頼します。テストカバレッジが目標水準（80%以上）を満たしているか、Lintエラーがないかなどの品質基準を機械的に確認させます。

### 7.4.4 プルリクエストとCIチェック
品質確認が取れたら、作業ブランチから `main` ブランチへのプルリクエストを作成します。GitHub Actions上でLintやテストのCIチェックが自動で走り、すべて「成功」となることを見届けます。

### 7.4.5 デプロイの実行
CIチェックが完了したらプルリクエストをマージし、GitHub Actionsの画面から手動でデプロイのワークフローを実行します。エージェントが用意したコードとインフラ定義によって、AWS環境へ自動的にアプリケーションがデプロイされます。

## 7.5 デプロイ後の動作確認
デプロイ完了後、AWS上で稼働しているシステムに対して最終的な品質確認を行います。

### 7.5.1 E2Eテストの実装
デプロイされた実際のURLに対して、Playwrightを用いたE2Eテストを実行する計画を立てます。ログイン画面へのアクセスや、メニュー管理画面の表示など、実際のユーザー操作をシミュレートするテストコードをエージェントに実装させます。

### 7.5.2 E2Eテストのデバッグ
作成したE2Eテストを実行し、失敗（Failed）した項目があればターミナルのエラー出力をClineに渡します。エージェントは「ロール制限の判定ロジックがおかしい」「画面のレンダリング待機時間が足りない」といった原因を解析し、修正コードを提案・適用します。

### 7.5.3 追加のE2Eテストと機能修正
テストと修正のイテレーションを繰り返し、必要に応じてコンテキストの圧縮（Compact Task）を挟みながら、すべてのE2Eテストがパスするまで品質を高めます。Lintや単体テストを含め、最終的にすべてのテストがグリーンになることを確認します。

## 7.6 商用リリースまでに取り組むべきこと
ここまでのハンズオンで基本的なデプロイと動作確認は完了ですが、実際の商用システムとして運用するにはさらに以下の対応が必要です。
*   **マルチ環境の整備**: Staging環境とProduction環境の分離。
*   **監視・ログ・アラート体制**: ログの粒度設定やアラート通知の仕組み構築。
*   **セキュリティの強化**: WAFの導入やAWS Secrets Managerでの機密情報管理。
*   **パフォーマンスとコスト最適化**: CloudFrontのキャッシュ戦略やAWS Budgetsの活用。
*   **運用体制の構築**: トラブルシューティングガイドなど運用手順書のドキュメント化。

## PART 7 Summary
PART7では、PART5とPART6で開発したアプリケーションをAWS環境にデプロイし、動作確認するまでのリリースプロセスを実践しました。
MCPサーバーを活用して最新のAWSナレッジとCDKベストプラクティスを取り入れ、`cdk-nag` によるセキュリティチェックも組み込みました。また、CI/CDパイプラインの構築やE2Eテストによる品質担保など、従来のソフトウェア開発における強固なガードレールとテスト駆動の作法が、Agentic Codingにおいても極めて重要であり、強力に機能することを確認しました。
