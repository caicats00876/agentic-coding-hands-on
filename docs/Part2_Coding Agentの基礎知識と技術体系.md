# PART 2 Coding Agentの基礎知識

LLMの基本概念を理解したところで、次にCoding Agentという技術領域について説明していきます。Coding Agentは、LLMの持つ能力をエンジニアリングタスクに特化して活用するAIエージェントです。

## 2.1 AIエージェントとは

### 2.1.1 AIエージェントの基本概念
AIエージェントとは、与えられた目標や指示に対して自律的に行動を決定し、環境と相互に作用しながらタスクを実行するAIシステムです。従来のプログラムのように事前に定義された処理フローに従うのではなく、自律性を持ち、状況を評価し、適切なアクションを選択して実行する能力を持ちます。

### 2.1.2 LLMベースのAIエージェント
LLMの言語理解能力により、「明日の東京の天気を調べて、傘が必要か教えて」のような曖昧で複合的な指示でも、意図を解釈し、必要なアクションを提案することができます。条件分岐を網羅的に記述する必要はなくなり、「どのようなコンテキストと制約を与えるか」へと移行しました。

### 2.1.3 ReAct (Reasoning and Acting)
ReActは、推論 (Reasoning) と行動 (Acting) を交互に繰り返し、複雑なタスクを段階的に解決するアプローチです。
*   **Thought（思考）**: 「考え」や「推論」を自由に内部で生成。
*   **Action（行動）**: 「Search」など外部環境操作をLLMが自発的に出力。
*   **Observation（観察）**: 外部APIやエージェントから得られた情報が返される。

### 2.1.4 エージェントの「ループ構造」
ReActで見たように、エージェントは「思考→行動→観察」のサイクルを繰り返します。すなわちエージェントの中核となる処理はループ構造であるとも言い換えられます。これを **Agent Loop**、あるいは **Agentic Loop** と呼びます。

### 2.1.5 エージェントの4つの特徴
*   **Profiling**: エージェントの役割や性格、専門分野などのプロファイル設定。
*   **Memory**: 短期記憶（会話履歴）と長期記憶（知識ベース）の管理。
*   **Planning**: 目標達成のための行動計画の推論、および行動結果を受けた計画の修正。
*   **Action**: 既存知識に基づく推論、およびTool Use/Function Callingの実行による行動。

## 2.2 Coding Agentとは

### 2.2.1 Coding Agentの定義
Coding Agentは、AIエージェントの中でもIT分野におけるエンジニアリングタスクに特化したエージェント、またはエージェント製品自体を指します。コードの読み書き、実行、デバッグ、テストなどの開発業務を担い、自律的な開発支援を目的としています。

### 2.2.2 Coding Agentの基本機能
単なるコード補完やチャットの応対を超えて、自律的にソフトウェアエンジニアとしての役割を果たします。開発者がLLMと対話しながらコードベースを参照していた従来のLLM Chatでの開発に対し、Coding Agentではエージェント自身がコードベースに直接アクセスし、ファイルの読み書きやコマンド実行を自律的に行います。

### 2.2.3 Coding Agentのタイプ
*   **IDE型**: 統合開発環境 (IDE) に統合された形で提供されるタイプ（例：GitHub Copilot、Cline、Cursor、Windsurfなど）。
*   **CLI型**: コマンドラインインターフェース (CLI) で動作するタイプ（例：Claude Code、OpenCodeなど）。
*   **非同期独立型**: ブラウザやクラウド上で独立して動作するタイプ（例：Devin、Julesなど）。

## 2.3 Context Engineeringとは

Coding Agentを効果的に動作させるには、LLMに与える情報（コンテキスト：Context）の設計が重要になります。コンテキストの5つの主要概念は以下の通りです。

### 2.3.1 プロンプトからコンテキストへ
LLMに与える情報すべて、すなわち「コンテキスト (Context)」全体をどのように設計し、管理するかという戦略を **Context Engineering** と呼びます。

### 2.3.2 Prompt
LLMに与えるコンテキストの出発点です。Coding Agentのシステムプロンプトには、①Coding Agent組み込み、②リポジトリ単位（ルールファイルなど）、③個人用途のカスタマイズ、の3種類があります。また、定型化されたユーザープロンプトとして「カスタムスラッシュコマンド」や「Agent Skills」が利用されます。

### 2.3.3 History
対話セッションにおける過去のやり取り（会話履歴）を短期記憶として扱います。入力の中間部分に位置する情報を見失う **Lost in the Middle（中間情報の欠落）** という現象を防ぐため、コンテキストを自動または手動で「圧縮」する技術が使われます。

### 2.3.4 Memory
会話履歴を超えた情報保持として、主に長期記憶と外部情報検索の2つの側面を表します。
*   **検索を利用する戦略 (RAG型)**: ベクトル化 (Embedding) を用いて関連するコードを横断的に検索する。
*   **専用ファイルに記録する戦略 (探索型)**: Markdownファイルなどに知識を保存し、必要に応じて読み込ませる。

### 2.3.5 Tool
外部環境へアクセスするために外部ツールを呼び出す仕組み (Tool Use / Function Calling) です。ファイルの読み書きやコマンドの実行などを行います。また、これらを標準化して外部システムと連携するためのプロトコルとして **MCP (Model Context Protocol)** が利用されます。

### 2.3.6 Output
出力形式をJSON、XML、表形式などの明示的な構造で指定することで、所定のUIで描画したり、他システムに連携しやすくします。

## 2.4 Coding Agentの機能の概念

### 2.4.1 計画策定
タスクの内容に応じてモードを切り替え、すぐ実装に移るのではなく対話を通じてタスク全体の進め方を整理する「計画策定モード (Plan)」が導入されています。`/deep-planning` コマンド等で設計書を文書として残す仕組みがあります。

### 2.4.2 Todoリスト
実施項目を検証可能な単体タスクに分解し、Todoリスト形式で管理することで、エージェントが目的を見失わずに自走力を高めることができます。

### 2.4.3 自動承認
開発速度のボトルネックとなる「ユーザー承認」フェーズをスキップし、ファイルの書き込みやコマンド実行を逐一承認させずにエージェントへ委ねる設定です。

### 2.4.4 コンテキスト補助
ユーザーが明示的に「このファイル・このフォルダを読んでください」と指示したい場合、`@path/to/file` のようなメンション構文や、エラーを参照する `@problems`、ターミナルを参照する `@terminal` などが利用できます。

## PART 2 Summary
PART 2では、Coding Agentを扱う上で必要となる基礎知識を整理しました。エージェントが自律的に動く仕組み (ReAct) や、IDE型・CLI型といったタイプ、そしてエージェントに与える情報を制御するContext Engineering (Prompt, History, Memory, Tool, Output) の5要素、さらには計画策定やTodoリストといった機能を理解することで、Coding Agentをより効果的に動かすことができます。
