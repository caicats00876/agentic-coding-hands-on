# Day3 チューター用ガイド

手順書：`docs/Day3_開発基盤構築と要件の具体化.md`

## この日のねらい

AI が品質を守りながら働ける土台（ルール、コマンド、テスト、Lint、CI）を作り、要件を AI と一緒に具体化します。

## ステップごとの確認点

### ハンズオン 1：CLAUDE.md とコマンドの配置

*   各ルールが、Day2 で見つけたどの問題を防ぐためのものかを、受講者に説明してもらいます。
*   **チームで話し合ったルールの代わり**：受講者が考えたルールを1つ以上、あなたとの対話で決めます。「Day2 で一番痛かった問題を防ぐには、どんなルールが必要か」と問いかけます。

### ハンズオン 2：Plan モードで計画を立てる

*   計画を**読まずに承認していないか**を確認します。根拠のある修正依頼を1つ以上出すよう促します。
*   レビュー観点（確認するコマンドがあるか、ライブラリの理由とライセンス、不要なものはないか）を1つずつ確認させます。

### ハンズオン 3：モノレポを構築する

*   環境の差で失敗しやすい工程です。エラーは要約せず、出力をそのまま AI に貼らせます。
*   イテレーションごとに、受講者自身がターミナルで `npm run check`、`npm run test`、`npm run build` を実行します。

### ハンズオン 4：CI と Pull Request

*   わざと Lint エラーを入れて、CI が失敗することまで確認させます。
*   ブランチ保護に「CI の成功を必須にする」を追加したかを、GitHub の画面で確認します。

### ハンズオン 5：要件から設計書を作る

*   AI から質問が来て受講者が答えられないときは、Day2 の「曖昧な点のメモ」に立ち返らせます。
*   設計書のレビュー観点（MVP の機能、受け入れ条件、状態遷移）を確認させます。

## 遅れたときの調整

| 状況 | 調整 |
| :--- | :--- |
| モノレポの構築が大きく遅れた | 原因をトラブル対応で切り分ける。リファレンス実装の雛形ブランチが用意されている場合は、それを merge する |
| 設計書が終わらない | 分割（split-design）を Day4 の朝に回す |
