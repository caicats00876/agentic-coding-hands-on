# Day2 チューター用ガイド

手順書：`docs/Day2_VibeCodingの限界とAgenticCodingへの転換.md`

## この日のねらい

午前は Vibe Coding のまま機能を追加させ、品質を自分で検証させます。ねらいは「壊れる体験」そのものではなく、**「今は動いている」と「この先も変更し続けられる」は別のこと**に、受講者自身が気づくことです。午後に「4つの作法」で解決の方向を示します。

試走では、受講者の認識が「見た目がまともだから納品できる」（朝）から「プロトタイプならこんなもの」（夕方）に変わりました。答えを教えるのではなく、問いかけで気づかせると効果があります。

## ステップごとの確認点

Codespace や VS Code の操作の説明は、Day1 で済んでいます。繰り返さず、分からなければ Day1 の手順書を見るよう案内します。

### 前日の振り返り（目安 15分）

*   日報の「AI が作ったアプリを、そのまま納品できるか」の答えを聞きます。答えは今日の最後にもう一度聞きます。

### ハンズオン 1：機能追加（60分で打ち切り）

*   Day1 と同じルール（コードを読まない、提案はそのまま承認）で進めます。
*   **60分で打ち切ります。**終わらないことも大切な記録です。
*   起動したあと、受講者がアクセスする URL を見つけられないことがあります。ポートタブの地球儀アイコンか、Claude Code に「URL を教えて」と聞くよう案内します。
*   2人のユーザーで確かめるときは、2人目をシークレットウィンドウで開かせます（同じウィンドウのタブではログイン状態が共有されます）。
*   **何も壊れなかった場合**（試走では、1回の指示、約10分、手戻り 0、デグレ 0 で完了した）：失敗ではないと伝え、次の問いで「今は動いている」と「守れる」の違いに目を向けさせます。
    *   「3か月後、別の担当者が機能を足したら、DM が第三者に届くようになりました。誰が、いつ気づきますか」
    *   「今日動いたことを、来月もう一度確かめるには、何をすればよいですか」

### ハンズオン 2：品質の検証

*   **AI に頼らせません。**受講者自身がターミナルでコマンドを実行します。
*   問いを出すたびに「Claude Code には聞かず、自分の言葉で」と添えます。Claude Code の答えが貼られてきたら、受け取らずに言い直してもらいます（試走で実際に起きた）。
*   Claude Code が頼まれなくてもテストを作っていることがあります（試走では `test/smoke.test.js`）。そのときは「テストがあるか」ではなく、次の3点に目を向けさせます。
    *   プロジェクトに残っているか（`npm run test` で動くか）
    *   変更のたびに自動で走るか（CI があるか）
    *   テストを実行することが、どこかに決めて書いてあるか
*   効いた問い：「AI が必ずテストを実行してくれる、と言える根拠はどこにありますか。決めてある場所はありますか」

### ハンズオン 3：問題点の4分類（目安 30分）

1.  受講者が一人で、見つけた問題を書き出し、4分類の表を埋めます。
2.  受講者は「特に問題ない品質」「プロトタイプなら十分」と判断しがちです。基準を「**今は動いているか**」から「**このまま変更し続けたときに守れるか**」に移す問いかけをします。
    *   「その問題は、どの時点で防げたと思いますか」
    *   「同じことがお客様の環境で起きたら、何が困りますか」
    *   「一番痛かった問題はどれですか。理由も教えてください」
3.  一番痛かった問題を、午後のミニ講義の導入に使います。

### ミニ講義：4つの作法（目安 30分）

*   スライドの 8 枚目（`…/agentic-coding-training.html#8`）を開いてもらい、午前に受講者が挙げた問題を、4つの作法の表に当てはめて説明します。
*   要点は「AI に気をつけてとお願いするのではなく、仕組みで強制する」です。

### ハンズオン 4：ガードレールの設定

*   **最初に、今ある `.claude/settings.json` の中身を見せます。**Day1 で確認ダイアログの「常に許可」を押していると、共有用の `.claude/settings.json` に `rm -rf`、`curl`、`npm i *` などが書き込まれていることがあります（試走で実際に起きた）。これを「読まずに許可した結果」の実例として使います。
*   コピーの前に Claude Code のパネルを閉じさせ、コピーのあとに `cat` で中身を確かめさせます。試走では、コピーした直後に「全部 allow」（deny と ask がない）に書き換わり、コピーし直したら再発しませんでした（原因は調査中。開いたままの Claude Code が古い設定で上書きした可能性があります）。
*   テンプレートは「正解」ではなく**体験用の例**だと伝えます。受講者から「この設定は研修として意味があるのか、正解なのか」と聞かれたら、「止まることと、すり抜けることの両方を体験するための例です」と答えます。
*   ガードレールは「禁止」ではなく、「**誰がどこで判断するかを先に決める**（deny は前もって決める、ask はその場の自分が決める、allow は前もって任せる）」ものとして伝えます。
    *   受講者から「`rm -rf`、`push --force`、`curl` も必要なら許可する」「確認ダイアログは数が少なくても読まない」という本音が出たら、否定せずに受け止めます。「人は読まない」ことを前提に、人の注意力に頼らない多層防御（Git、Codespaces、ブランチ保護）につなげます。
*   `.claude/settings.json` をコミットしたかを確認します（提出物に含まれる）。`git add -A` ではなく、ファイルを指定してコミットさせます（`hello/` などが混ざらないように）。

### ハンズオン 5：危険な操作が止まることを確かめる

*   AI が `cat` などで `.env` を読もうと回り込むことがあります。
*   AI が**受講者に抜け道を提案する**こともあります（試走では「`.env` は `cat` なら読める」「`rm -r -f` や `find -delete` なら通る」「`--force-with-lease` は deny に一致しない」）。「権限設定は文字の並びでしか止められない」ことの実例として扱い、ブランチ保護の導入につなげます。
*   AI が拒否された操作を何度も試すときは、会話を止めて、受講者自身にターミナルで実行させます。
*   ブランチ保護は、受講者の fork の `main` に設定します。

### ハンズオン 6：Plan モードで直す

*   直す不具合がない場合は、`hands-on/day2/plan-alternative.prompt.txt`（ユーザー名の20文字の数え方）を使わせます。試走では、調査の結果、画面、サーバー、保存の3か所で数え方がばらばらだと分かりました。
*   承認の選択肢は「Yes, and manually approve edits」を選ばせます。
*   計画を**読んでから**承認させます。次の観点を確認させます。
    *   頼んでいない作業が入っていないか（試走では、頼んでいない NFC 正規化、文字数表示、E2E とスマホ幅、Playwright の追加が入っていた）
    *   追加するライブラリの版は新しいか、脆弱性はないか（試走では `@playwright/test@1.49.1` に high の脆弱性が2件あり、AI が `npm audit` で気づいて質問してきた。最終的に新しい版に固定した）
*   受講者は「Vibe Coding との違いが分からない」「自分で決めたことはない」と答えがちです（AI が選択肢とおすすめを出すため）。「**計画の中に、自分が知らなかった事実や頼んでいない作業がいくつあったか**」を数えさせ、それが Vibe Coding では見えていなかったことに気づかせます。
*   想定問答：ライブラリの版の選び方について、ゼロデイ攻撃やワンデイ攻撃の観点で質問されることがあります。「公開直後の版を2週間待つ」はサプライチェーン攻撃には有効ですが、既知の脆弱性を突くワンデイ攻撃に対しては逆向きのリスクになります。ここは深追いせず、「Day3 で CI に `npm audit` を入れて、継続して確かめる仕組みにする」とつなげます。

### ハンズオン 7：要件を読む（目安 30分）

*   読む範囲は「コア機能」と「非機能要件」です。受講者が技術スタックの説明を求めてきたら、「今日探すのは、何を作るかのあいまいさです」と範囲を戻します。
*   「MVP」が通じないことがあります。要件の冒頭と「コア機能」の下に「必ず作る範囲」と書いてあります。これ自体を「人によって通じない言葉」の例として使えます。
*   あなたが「この言葉を AI はどう解釈すると思うか」と問いかけ、受講者なりの答えをメモにまとめさせます。Day3 で AI から質問されたときに使います。
*   試走で出た例：「注文画面を使うのはお客さんか店員か、どの機器か」が要件にない。受講者は「お客さんが自分のスマートフォンで使う」と決めた。すると「席の選び方」や「Codespaces の Private ポートにお客さんのスマホからどうつなぐのか」が新しい問いになる。この矛盾は Day3 の要件の具体化で扱います。

### 記録

*   比較シートの「Vibe Chat」列がすべて埋まったか、日報を書いたかを確認します。記入は、あなたが示すひな形を貼って数字を書き込む形にします。
*   最後に、朝の「そのまま納品できるか」をもう一度聞き、答えが変わったかを確かめます。

## 遅れたときの調整

| 状況 | 調整 |
| :--- | :--- |
| 機能追加が60分で終わらない | 打ち切る（予定どおり） |
| 機能追加がすぐ終わり、何も壊れない | 上の問いで「守れるか」に目を向けさせ、品質検証に早めに進む |
| 午後が押した | ハンズオン 7 の一部を Day3 の朝に回す |
